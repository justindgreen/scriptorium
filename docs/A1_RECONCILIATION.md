Proposed as two short milestones so the sheet and tracker stop being confusing before Phase 3 builds on them. Both keep the engine and command path as they are.

**UX-1 (size M): safety and clarity on the sheet.**

- #6 confirmation dialogs for long rest and level-up, each stating what will change and that it is not undoable.
- #15 level-up rollback: a `characters.revertLevelUp` procedure that, in one transaction, re-checks that the latest event is the level-up and the latest snapshot is `level_up` at revision − 1 with no later events, then runs the existing `restoreSnapshot` command (logged, non-reversible). The Undo panel offers it only when the server reports it available. Nothing becomes a general undo.
- #10 inactive-effect badge from `sheet.items.inactiveReason` with an Attune button beside it (the data already exists since M2.7).

## 6. Architectural and security implications

- **Condition synchronization (#13).** The defect is a second source of truth, not a missing feature. The fix must delete the duplicate rather than mirror it: character participants carry no conditions of their own. Mirroring would reintroduce the drift after any sheet edit, restore or undo.
- **Level-up rollback (#15).** Safe only if the server re-validates atomically under the character row lock: latest event is `addClassLevel` (or `setSubclass` as part of the same step), the newest snapshot has reason `level_up` and `revision === current − 1`, no events after it. The command stays a logged, non-reversible `restoreSnapshot`; the undo window and reversibility rules are unchanged.
- **Hidden combatants and the player split (#17, #20).** The dependency runs one way: #20 (UX-2) builds the player serializer that returns only revealed participants, no events and no placeholders; #17 (M5.3) adds the DM's hide and reveal controls on top of that filter and never the other way round. Visibility is a server property of the participant (`visibleToPlayers` already exists) applied in the role serializer and in every derived response: participants, events, subscriptions, attack options and any future notification. The player log is removed entirely for players rather than filtered, which is simpler to prove. Tests must assert the absence of hidden participants, not just of fields.
- **Mid-combat additions (#16).** Turn ids are `encounter:round:index`; inserting a participant changes indices. The insertion must keep the current participant current (recompute `turnIndex` from the current participant id, not the other way round) and must not issue `turnStarted` to anyone; otherwise once-per-turn marks reset mid-turn.
- **Multi-collection identity (#12).** A content uid is the publisher's identity and a pinned `version_id` is what characters hold; collections are organizational membership only. Any design that renames or moves uids to change access would break pinning and must be refused.
- **Delegated editing (#1).** The current DM allow-list is the extension point; widening it to full editing needs the audit trail (actor id on every event already exists) and a visibility layer separate from editing authority, so a shared sheet can be read without being editable.
- **Ability rolls (#3).** Rolling must happen on the server with the cryptographic RNG and be recorded in `rolls`, like hit dice; the engine stays pure and the browser never rolls.
